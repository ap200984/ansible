# Google IPv4 routing through VDS6

Four GRE tunnels use OSPF loopbacks as their outer endpoints. VDS7_CHR and
both LAN-only Logia routers are excluded. Tunnel addresses use 10.250.4.0/24;
10.250.4.8/30 remains unallocated.

| MikroTik | Subnet | Router GRE IP | VDS6 GRE IP | VDS6 interface |
| --- | --- | --- | --- | --- |
| K16_112 | 10.250.4.0/30 | 10.250.4.1 | 10.250.4.2 | gre-k16 |
| 3Ekipazhnyi64 | 10.250.4.4/30 | 10.250.4.5 | 10.250.4.6 | gre-3ekip |
| k16_21 | 10.250.4.12/30 | 10.250.4.13 | 10.250.4.14 | gre-k21 |
| Misha | 10.250.4.16/30 | 10.250.4.17 | 10.250.4.18 | gre-misha |

Each MikroTik uses interface `gre-vds6`, local endpoint 10.255.0.N and remote
endpoint 10.255.0.6. MTU is 1300, TCP MSS is clamped, and GRE FastPath is off.
The GRE interfaces carry policy traffic, not OSPF. Underlay OSPF/BFD continues
on the existing WG/AWG/PPP links, so GRE cannot recursively become its own
route to a loopback endpoint.

`get_google_ips` downloads [Google's authoritative prefix feed](https://www.gstatic.com/ipranges/goog.json)
with HTTPS certificate validation and parses its `ipv4Prefix` entries. The
script validates the complete result before changing `google_ips`; on download
or parse failure it retains the last good list. A daily scheduler runs at 01:00
in each router's configured time zone. The list includes all Google IPv4 ranges
published in this feed. IPv6 prefixes require separate IPv6 policy routing and
are not placed in an IPv4 firewall address list.

Google traffic from `LAN` and traffic generated by the router is marked for
`google_ips_table`. Its primary default goes through the router's own VDS6 GRE
peer, with ping gateway checking. A blackhole default prevents main-table WAN
fallback when that peer is unreachable. Previous Google SSTP/VPN marking rules
and the old K16 Google default are disabled. Other destination policies remain.
Google connections are excluded from IPv4 forwarding FastTrack.

Google Internet traffic is source-NATed to the router's GRE address, then
masqueraded on VDS6's WAN (`eth0`). This makes the return path deterministic,
including Misha's unadvertised 192.168.0.0/24 LAN. Routed private 10/8 traffic
retains its existing no-source-NAT policy. VDS6 accepts established return
traffic to each GRE interface and clamps TCP MSS to 1260.

## Deployment and restoration

Run `google-gre.yml` with the vds6 inventory, pinned SSH host keys and a trusted
`router_proxy_command` when the management jump host is required. It installs
persistent VDS6 services first, refreshes the prefix lists, enables each router
GRE, verifies its peer, then switches Google traffic. Existing Google sessions using the former NAT
path are reset selectively; unrelated connections and valid GRE sessions stay
in place. The former disabled K16
GRE and its Linux `gre-k16.service` are reused.

Address allocation is in `vars/google-gre.yml`; router and VDS6 host variables
record the enabled state. Readable updater/policy templates and Linux helpers
are in `mikrotik/templates` and `roles/google-gre`. Full router captures and
encrypted restore manifests preserve the deployed state. The existing
`restore-vds-routing.yml` restores the VDS6 GRE helpers, units and forwarding
firewall; MikroTik `apply.yml` restores router GRE, scripts and policy records.
The topology drawing includes these four additional GRE links.

Validation on 2026-10-11: all four GRE peers and Google 8.8.8.8 pings passed;
all four routers completed Google HTTPS requests with certificate validation.
A real K16 LAN client (10.9.0.70) also returned HTTPS status 204. Each
`google_ips` list contains exactly the 130 IPv4 prefixes in Google's official
feed. All 90 directed OSPF loopback checks passed and all 50 BFD endpoints
remained Up. All five VDS6 GRE/firewall services are active and enabled at boot.

## Check the Google egress IP in a browser

Open https://api.ipify.org from a client behind any of the four routers.
The expected IPv4 address is `195.245.239.82` (VDS6). This IPv4-only endpoint
returns plain text, so an IPv6 connection cannot bypass the IPv4 GRE test.

`google_gre_check_hostname` in `vars/google-gre.yml` controls the hostname.
RouterOS resolves its FQDN address-list entry and maintains dynamic IPv4
entries in `google_gre_ip_check`. Dedicated LAN/output marking, forwarding and
source-NAT rules use the same `google_gre` connection mark, `google_ips_table`
and GRE gateway as Google traffic, including its blackhole fallback. The
Google prefix updater leaves this separate list intact.

Use the router's DNS resolver when testing: browser Secure DNS or another
resolver can return different addresses from those learned by RouterOS.
A browser proxy or VPN can also change the observed path. An IP-check request
confirms this policy's egress; it does not check every individual Google prefix.

Validation: HTTPS checks from all four routers and a real K16 LAN client
returned `195.245.239.82` on 2026-10-11.

## Telegram, ChatGPT, WhatsApp and Instagram

VDS6's public IPv4 address (`195.245.239.82`) also uses GRE from LAN clients
and the routers themselves. The `vds6_public_ip` list uses the same policy
table, connection marks, forwarding and source NAT rules. Replies return to
each router's GRE address. The GRE outer endpoint remains `10.255.0.6`, so
routing the public address through GRE does not create tunnel recursion.
Both GRE deployment playbooks apply this policy.

Validated on 2026-10-12: all four routers reached `195.245.239.82` with
three of three ping replies, and their public-IP routing/source-NAT counters
confirmed GRE use. K16 LAN traffic also matched the new routing and NAT rules.

`service-gre.yml` deploys additional services on the same four GRE routers;
`google-gre.yml` includes this configuration during full restoration. The
LAN-only Logia devices and CHR are outside this scope.

`get_telegram_ips` downloads https://core.telegram.org/resources/cidr.txt over
certificate-validated HTTPS. It validates IPv4 networks and a minimum prefix
count before replacing `telegram_ips`; failures preserve the previous list.
IPv6 feed entries are skipped. Telegram web/link domains also learn addresses
through DNS into the same list; feed refresh preserves these dynamic entries. The scheduler runs daily at 01:05 in each
router's time zone. The feed hostname itself has a separate DNS-maintained
`telegram_feed_ips` list routed through GRE, since direct ISP access timed out.

`get_meta_ips` refreshes `meta_ips` from Meta's AS32934 every day at 01:10
in each router's time zone. It uses [RIPEstat RIS Prefixes](https://stat.ripe.net/docs/data-api/api-endpoints/ris-prefixes)
with originating IPv4 prefixes only (`types=o`, `af=v4`, `noise=filter`),
excluding transit networks. The compact JSON response fits RouterOS fetch's
in-memory output limit. HTTPS certificates, API status, returned ASN, prefix
syntax and count are checked before updating the list; at least 50 prefixes
are required. Download/validation failures retain the last good list. New
prefixes are added before obsolete static entries are removed. Overlapping
updater jobs are rejected.

All four GRE routers route `meta_ips` from LAN and router output using the
existing GRE table, forwarding, source NAT and FastTrack exclusion. The updater
hostname has its own `meta_feed_ips` policy so refreshes also use GRE. Both
GRE playbooks install the updater, refresh immediately and selectively reset
old Meta sessions. Existing DNS lists remain supplementary; destinations in
`meta_ips` no longer depend on clients querying the router's DNS. This routes
other AS32934 services, including Facebook, as well as WhatsApp and Instagram.
IPv6 and destinations outside this ASN are outside this prefix policy.

`service_gre_dns_domains` in `vars/google-gre.yml` defines DNS FWD entries with
subdomain matching. DNS list retention uses TTL plus one day (matching the existing K16/Misha
setting) so short-lived DNS answers remain useful across client caches.
Client answers automatically populate `chatgpt_ips`,
`whatsapp_ips`, `instagram_ips` and `meta_shared_ips`. These entries use the
router's normal upstream DNS configuration, including existing DoH. On Misha,
matching legacy localhost forwarding entries are replaced. 3Ekipazhnyi64 DHCP
now advertises only 10.10.0.1 as DNS; renewed leases remove external fallbacks.
Other routers already advertise their own resolver.

The shared Meta list includes fbcdn.net, fbsbx.com, facebook.com and
facebook.net for common media/authentication dependencies. Some Facebook or
unrelated shared-CDN traffic can therefore use GRE as well. ChatGPT domains
include dependencies from OpenAI's published network recommendations:
https://help.openai.com/en/articles/9247338-network-recommendations-for-chatgpt-errors-on-web-and-apps

Each service list has LAN and router-output connection/routing marks,
forwarding and source-NAT rules. They share `google_gre`, `google_ips_table`,
the existing per-router GRE peer and blackhole fallback. Old mangle rules for
these same lists are disabled. Common connection-mark routing rules keep
established GRE sessions on this path after a learned DNS address expires. Only stale matching pre-GRE IPv4 sessions are
reset, preserving unrelated and already healthy GRE connections.

Clients must query the router's DNS. Browser Secure DNS, Android Private DNS,
third-party resolvers, cached answers and direct-IP app connections can bypass
learning. Renew leases/restart apps as needed. This remains an IPv4 policy;
IPv6 and peer-to-peer voice/video paths are not guaranteed to traverse VDS6.

To reapply just these router policies (with existing GRE tunnels), run from
this repository and supply your trusted jump-host connection variables:

```sh
ANSIBLE_LIBRARY="$PWD/mikrotik/library" \
ANSIBLE_MODULE_UTILS="$PWD/mikrotik/module_utils" \
ansible-playbook -i localhost, service-gre.yml -e @/path/to/router-connection.yml
```

The connection file defines `router_proxy_command` as documented in the
MikroTik README. SSH host keys remain pinned in `mikrotik/known_hosts`.
