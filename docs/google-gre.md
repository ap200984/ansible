# Google IPv4 routing through VDS6

Four GRE tunnels use OSPF loopbacks as their outer endpoints. VDS7_CHR and
both LAN-only Logia routers are excluded. Tunnel addresses use 10.250.4.0/24;
10.250.4.8/30 remains unallocated.

| MikroTik | Subnet | Router GRE IP | VDS6 GRE IP | VDS6 interface |
| --- | --- | --- | --- | --- |
| K16_112 | 10.250.4.0/30 | 10.250.4.1 | 10.250.4.2 | gre-k16 |
| 3Ekipazhnyi64 | 10.250.4.4/30 | 10.250.4.5 | 10.250.4.6 | gre-3ekip |
| k16_21 | 10.250.4.12/30 | 10.250.4.13 | 10.250.4.14 | gre-k21 |
| Misha | 10.250.4.16/30 | 10.250.4.17 | 10.250.4.18 | gre-misha |

Each MikroTik uses interface `gre-vds6`, local endpoint 10.255.0.N and remote
endpoint 10.255.0.6. MTU is 1300, TCP MSS is clamped, and GRE FastPath is off.
The GRE interfaces carry policy traffic, not OSPF. Underlay OSPF/BFD continues
on the existing WG/AWG/PPP links, so GRE cannot recursively become its own
route to a loopback endpoint.

`get_google_ips` downloads [Google's authoritative prefix feed](https://www.gstatic.com/ipranges/goog.json)
with HTTPS certificate validation and parses its `ipv4Prefix` entries. The
script validates the complete result before changing `google_ips`; on download
or parse failure it retains the last good list. A daily scheduler runs at 01:00
in each router's configured time zone. The list includes all Google IPv4 ranges
published in this feed. IPv6 prefixes require separate IPv6 policy routing and
are not placed in an IPv4 firewall address list.

Google traffic from `LAN` and traffic generated by the router is marked for
`google_ips_table`. Its primary default goes through the router's own VDS6 GRE
peer, with ping gateway checking. A blackhole default prevents main-table WAN
fallback when that peer is unreachable. Previous Google SSTP/VPN marking rules
and the old K16 Google default are disabled. Other destination policies remain.
Google connections are excluded from IPv4 forwarding FastTrack.

Google Internet traffic is source-NATed to the router's GRE address, then
masqueraded on VDS6's WAN (`eth0`). This makes the return path deterministic,
including Misha's unadvertised 192.168.0.0/24 LAN. Routed private 10/8 traffic
retains its existing no-source-NAT policy. VDS6 accepts established return
traffic to each GRE interface and clamps TCP MSS to 1260.

## Deployment and restoration

Run `google-gre.yml` with the vds6 inventory, pinned SSH host keys and a trusted
`router_proxy_command` when the management jump host is required. It installs
persistent VDS6 services first, refreshes the prefix lists, enables each router
GRE, verifies its peer, then switches Google traffic. Existing Google sessions using the former NAT
path are reset selectively; unrelated connections and valid GRE sessions stay
in place. The former disabled K16
GRE and its Linux `gre-k16.service` are reused.

Address allocation is in `vars/google-gre.yml`; router and VDS6 host variables
record the enabled state. Readable updater/policy templates and Linux helpers
are in `mikrotik/templates` and `roles/google-gre`. Full router captures and
encrypted restore manifests preserve the deployed state. The existing
`restore-vds-routing.yml` restores the VDS6 GRE helpers, units and forwarding
firewall; MikroTik `apply.yml` restores router GRE, scripts and policy records.
The topology drawing includes these four additional GRE links.

Validation on 2026-10-11: all four GRE peers and Google 8.8.8.8 pings passed;
all four routers completed Google HTTPS requests with certificate validation.
A real K16 LAN client (10.9.0.70) also returned HTTPS status 204. Each
`google_ips` list contains exactly the 130 IPv4 prefixes in Google's official
feed. All 90 directed OSPF loopback checks passed and all 50 BFD endpoints
remained Up. All five VDS6 GRE/firewall services are active and enabled at boot.

## Check the Google egress IP in a browser

Open https://api.ipify.org from a client behind any of the four routers.
The expected IPv4 address is `195.245.239.82` (VDS6). This IPv4-only endpoint
returns plain text, so an IPv6 connection cannot bypass the IPv4 GRE test.

`google_gre_check_hostname` in `vars/google-gre.yml` controls the hostname.
RouterOS resolves its FQDN address-list entry and maintains dynamic IPv4
entries in `google_gre_ip_check`. Dedicated LAN/output marking, forwarding and
source-NAT rules use the same `google_gre` connection mark, `google_ips_table`
and GRE gateway as Google traffic, including its blackhole fallback. The
Google prefix updater leaves this separate list intact.

Use the router's DNS resolver when testing: browser Secure DNS or another
resolver can return different addresses from those learned by RouterOS.
A browser proxy or VPN can also change the observed path. An IP-check request
confirms this policy's egress; it does not check every individual Google prefix.

Validation: HTTPS checks from all four routers and a real K16 LAN client
returned `195.245.239.82` on 2026-10-11.
